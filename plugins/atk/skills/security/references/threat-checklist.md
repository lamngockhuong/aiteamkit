# Threat checklist

Loaded by `atk:security` in steps 1, 2, 3 and 5. The controls to find before any candidate, what to
run, what to ask at each trust boundary and in which order, and the baseline checklist a review
answers when nobody supplied one.

The questions here are stack-agnostic on purpose. How a control is written differs per framework;
whether it exists does not, and a question that names one framework's function reads as settled on
every project that does not use it.

## Finding the commands

Look for each command in this order and use the first that answers. Record which one it was.

1. The Commands section of `.atk/profile.md`.
2. A CI workflow that already runs it: `.github/workflows/`, `.gitlab-ci.yml`, or the project's
   equivalent. A job that fails the build on it is the project's gate, and what it passes is what
   the team has agreed to ship.
3. A script in the manifest whose name says it: `audit`, `security`, `scan`.
4. The package manager's own audit command, when its lockfile is in the repository. Say that it was
   this skill's choice, because the team never agreed that its threshold is theirs.

A scanner the project does not have is not installed quietly. Name it, say what it would add, and
ask. A run that installs a tool leaves the repository or the machine different from how the team
left it, and the next person cannot tell why.

## Global controls and trust assumptions

Loaded in step 1, before any candidate exists. A review that hunts for findings before it knows what
the project already applies to every request reports the same gap the framework closed, on every
route, and a reviewer stops reading at the third one.

Find the controls by the role they play, not by the name a framework gives them:

- What authenticates a request before a handler runs: a middleware, a filter, a gateway, a guard
  registered once for a group of routes.
- What authorises it: a policy layer, a role check applied by decorator or configuration, a query
  scope that adds the owner to every read.
- What validates input: a schema applied at the boundary, a binding layer that rejects unknown
  fields.
- What builds a query or a command: an ORM or a query builder that binds values, a wrapper around
  the shell.
- What renders output: a template engine that escapes by default, a serialiser that drops fields not
  listed.
- What the configuration applies to every response: security headers, cookie defaults, cross-origin
  rules, rate limits.

Record each with `path:line`, where it is applied and what it is applied to, and the narrow gap where
a finding is still possible: a validation layer that never sees raw headers, a query builder that
binds its own template but not the raw call beside it, a guard registered for every route except the
ones added after it. The gap is where the review looks; the rest of the surface that control covers
is cited, not walked again. A control the change under review removes, narrows, or bypasses is a
finding in itself, whatever the rest of the review finds.

These are taken as given on every project, so a candidate that rests only on one of them being false
is not a finding:

- Configuration set by whoever deploys the system is trusted input. A value read from the
  environment is not attacker-controlled unless something a caller sends reaches it.
- A random identifier generated by the platform's secure random source is not guessable.
- Output rendered by a framework that escapes by default is escaped, unless the code opts out at
  that line.
- A check made only in the client is a convenience, not a control. A candidate that rests on it is
  judged as if the check were absent.

Not reported without a concrete path from an entry point, through the code, to an impact:

- A timing difference or a race argued from the shape of the code alone.
- Server-side request forgery where the caller controls only the path, not the host or the scheme.
- "Hardening is missing", a header, a flag, a limit, with no attack it would stop in this scope.
- A dangerous function by name, with no input traced to it.

Each of these can still be a `PLAUSIBLE` finding when the mechanism is named and the one check that
would settle it is stated, per `references/record-template.md`. What it cannot be is a finding on its
own shape.

## Reading order per boundary

Walk each boundary in this order, which is the order findings are most often found in. A review cut
short still reads the places most likely to hold one.

1. Routes against their guards: every entry point, and the authentication and authorisation applied
   to it.
2. Roles against the project's own authorisation documents: what the reference documents step 1
   found, or the design, say each role may do, and what the code lets it do.
3. Access to an object by an identifier the caller sends: whether the owner or the tenant is checked
   at that read and that write.
4. Every error path of a security check: what happens when the check throws, times out, or returns
   nothing.
5. Raw queries, shell commands, dynamic evaluation, and deserialisation of what a caller sent.
6. Input that reaches a use without passing the validation the global controls apply.
7. The client surface: what the browser or the app stores, renders unescaped, or redirects to.
8. Configuration and infrastructure the scope ships: the shipped configuration check, the CI
   pipeline, the container or the deployment manifest.
9. Cryptography, limits, and logging.

## Automated checks

| Check | How | A finding when |
|-------|-----|----------------|
| Dependency audit | The command found above | It reports a known vulnerability in a package the scope ships. Whether it ships is decided from the production dependency tree of each deployable, named in the record, not from a development flag the audit tool prints; a tree that could not be built leaves the answer unknown, never development-only. Two signals are findings as well: an override or a pin that is itself still vulnerable, and an advisory with no published patch, where mitigating or accepting it is a decision for a role, not for this skill |
| Secrets in tracked files | The `tree` scan of `shared/secret-scan.md`, over every tracked file rather than the staged diff. It prints path, line and shape and never the line, and the line is not opened in the session: the record cites the path, the line and the shape, and the person who owns the file opens it and says whether the value is live | A line matches, unless that person says it is a placeholder or a read from the environment. An example file counts like any other: a placeholder in it is not a finding, a live value is |
| Tracked environment file | `git ls-files` for the paths that file lists as findings on their own | Any of them is tracked, whatever it holds today |
| Secrets in history | Only with a history scanner the project already has | Never claimed as clean when no such scanner ran; the record says history was not scanned |
| Shipped configuration | Read the configuration the scope deploys | Debug mode on, a wildcard origin with credentials, a default password, a verbose error page in a production profile |

## STRIDE per boundary

Ask all six at every trust boundary step 1 named. The answer is a line of the record either way.

| Question | Ask | Where it usually fails |
|----------|-----|------------------------|
| Spoofing | Can a caller claim to be someone they are not? | Unverified tokens, a session that survives logout, a callback nobody signs |
| Tampering | Can a caller change what they should only read, or change it in transit? | Input used in a query or a command without binding, a client-side price, an unsigned webhook |
| Repudiation | Could an actor deny an action, and would the logs contradict them? | No record of who changed a permission, logs anyone can edit |
| Information disclosure | Can a caller see what is not theirs? | Another user's record by changing an ID, a stack trace in a response, personal data in a log line |
| Denial of service | Can one caller exhaust what everyone shares? | No limit on an expensive endpoint, an unbounded list, a pattern that backtracks |
| Elevation of privilege | Can a caller do what their role may not? | A check in the screen but not in the handler, an administrator route behind the ordinary guard, a role the project's authorisation documents deny an action that the code lets it take |

## OWASP Top 10 map

After the STRIDE pass, map each candidate to the category a client checklist is most likely to use,
the current edition of the OWASP Top 10, which is the 2025 one. Cite an ID with its edition,
`A05:2025`, because the same number names a different category in another edition and a record is
read years after it was written. When OWASP publishes a new edition, this table is derived again
from the official pages rather than renumbered by hand. The map is for the reader, not a second
pass: a category with no candidate is not searched again for its own sake.

| ID | Category | Usually surfaced by |
|----|----------|---------------------|
| `A01:2025` | Broken Access Control | Elevation of privilege, information disclosure, and tampering where the server fetches a URL a caller gave, which this edition maps here rather than to a category of its own |
| `A02:2025` | Security Misconfiguration | The shipped configuration check |
| `A03:2025` | Software Supply Chain Failures | The dependency audit, and the CI pipeline: actions pinned to a commit rather than a moving tag, the permissions a workflow grants, how a secret reaches a step |
| `A04:2025` | Cryptographic Failures | Information disclosure, the secrets check |
| `A05:2025` | Injection | Tampering |
| `A06:2025` | Insecure Design | Any boundary where the control is missing rather than broken |
| `A07:2025` | Authentication Failures | Spoofing |
| `A08:2025` | Software or Data Integrity Failures | Tampering at a build, an update, or a deserialisation |
| `A09:2025` | Security Logging and Alerting Failures | Repudiation |
| `A10:2025` | Mishandling of Exceptional Conditions | Any security check whose error path falls through to allow, such as a `catch` around an authorisation or signature check that carries on as if it passed |

## Baseline checklist

Answered in step 5 when no `--checklist` was given. Keep the IDs, so a later record can say which
item changed.

| ID | Item |
|----|------|
| SEC-01 | Every entry point in scope requires authentication, or is recorded as public on purpose |
| SEC-02 | Authorisation is checked on the server for every action and every record, not only in the screen |
| SEC-03 | Input reaching a query, a command, a file path, or a template is bound or validated at that use |
| SEC-04 | Passwords are stored with a slow, salted hash; tokens expire and are checked on the server |
| SEC-05 | No credential is in a tracked file, and no environment file is tracked |
| SEC-06 | Personal data is limited to what the feature needs, and none of it reaches a log |
| SEC-07 | Errors shown to a caller carry no stack trace, query, or internal path |
| SEC-08 | Expensive or public endpoints are rate limited, and every list is bounded |
| SEC-09 | Security-relevant actions are logged with the actor and the time |
| SEC-10 | Dependencies carry no known vulnerability at the severity the project blocks on |
| SEC-11 | Shipped configuration has debug off, no default credential, and origins restricted |
| SEC-12 | Calls to and from third parties are authenticated, and callbacks are verified |
| SEC-13 | Session cookies carry the secure, http-only and same-site attributes, and state-changing requests are protected against cross-site request forgery |
| SEC-14 | Redirects go only to an allowed list or a relative path, and a session ends on the server at logout |
| SEC-15 | Authentication is protected against brute force |
| SEC-16 | Uploads are limited in size and count |

A client or company checklist replaces this list rather than being added to it. Where it leaves out
something this list has, say so in one line under the checklist rather than answering both.
