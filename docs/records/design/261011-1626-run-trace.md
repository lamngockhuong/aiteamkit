# Every atk skill leaves a run trace by default, and atk:tailor --feedback reads many of them

## In short

Today the only way to improve a skill from experience is `atk:tailor --feedback`, and it can read
only the run that happened in the current session. A run in a subagent, in another agent's CLI, or
in yesterday's session leaves nothing it can read, and `atk:orchestrate`, designed in
`docs/records/design/261011-1538-orchestrate-team-work.md`, would produce dozens of such runs at a
time.

This design gives every skill a **run trace**: a short file of fixed-shape lines, written as the run
goes. Each line records an observable fact:

- which step ran or was skipped, and why;
- which question went to which person, and how long it waited;
- where a ceiling stopped the run;
- what a review found;
- what a person corrected afterwards, in that person's words.

It is on by default. A project turns it off with one line in `.atk/profile.md`, `Run trace: off`.
`atk:tailor --feedback` gains `--runs`, which reads many traces of one skill and puts each pattern it
finds through the fork it already has: an override for this team, a record for the skill's author,
or neither.

No new skill is added. The rule that every skill writes a trace becomes rule 10 of
`plugins/atk/shared/team-roles.md`, and its shape lives in a new `plugins/atk/shared/run-trace.md`.

## Current state

- **`atk:tailor --feedback` reads one session.**
  - With no skill named, it takes the skill "from the session: the skill of this kit that ran in it"
    (`plugins/atk/skills/tailor/SKILL.md:200`).
  - Its record describes one run in a table and counts findings across the three outcomes
    (`SKILL.md:175-180`; `plugins/atk/skills/tailor/references/feedback.md`, "What the record
    holds").
  - It sorts every finding one at a time into an override, a record for the author, or neither
    (`SKILL.md:181-184`; `feedback.md`, "The fork").
  - The record goes to `docs/derived/feedback/<skill>-<date>.md` (`SKILL.md:233`). It reaches the kit
    repository only when the user asks (`SKILL.md:250-251`).
- **Three skills already write a log, for a different purpose.**
  - `atk:fix`, `atk:verify` and `atk:implement` write a progress log at
    `docs/derived/<skill>/<run-id>/progress.md` so that a run can resume
    (`plugins/atk/shared/artifact-paths.md:316-325`). It records one entry per unit of work, masked
    under rule 9 (`:341-347`).
  - Its path goes into the local exclude file and is confirmed with `git check-ignore -q`
    (`:325-333`).
  - It is never staged (`:373-376`).
  - It records what a resume needs, not what an analysis needs. It holds no step list, no wait times,
    and no corrections. The other twenty-one skills write none.
- **`atk:run-cases` has a "run log" of its own,** with its own shape
  (`plugins/atk/skills/run-cases/references/execution.md:128`; `artifact-paths.md:320-321`). That is
  why this design does not use the name.
- **One line in the profile already changes behaviour.** `Contract: first` or `Contract: code` in
  Docs "is the one entry there that changes what a skill does rather than where it writes", and a
  missing line has a defined reading (`plugins/atk/shared/project-profile.md:200-203`).
- **Ten skills run without a profile** (`project-profile.md:212-228`), so a rule that depends on a
  profile line has to say what a missing profile means.
- **Rule 9** keeps secret values, `.env` files, and the files of its list out of the session and out
  of everything a run writes, including what a spawned agent returns (`team-roles.md:95-121`).
- **Every skill cites `team-roles.md`** (`CLAUDE.md`, the `shared/` table). Its nine rules are read by
  every run.

## Decision criteria

1. **Covers unwatched runs** (AC2).
2. **Data that can be counted**: the same fields in every trace, so a pattern across runs is visible.
3. **Gates and privacy intact** (AC5).
4. **Fit with the kit**: no rule in a hook, the DRY layer, and the persistence groups.
5. **Cost to every run**, since it is on by default (AC3).
6. **Effort and reversibility.**

## Options

### Option A: keep today's `tailor --feedback` (the default)

- Unwatched runs: **no**. It reads one session.
- Countable: no; each record is one run.
- Cost: none.

It fails AC1 and AC2.

### Option B: a journal skill, invoked after a run

A twenty-sixth skill writes a narrative entry: what happened, what was decided, what comes next.

- Unwatched runs: **no**. Somebody has to invoke it after each of dozens of jobs, and nobody will.
- Countable: no. Prose written after the fact by the agent that ran does not show that step 5 was
  skipped in nine runs out of twelve.
- Fit: it duplicates the judgement `tailor --feedback` already makes.

### Option C: read the harness's own transcripts

The harness keeps session files on disk.

- Unwatched runs: partly, on the harnesses that keep them, each in its own format.
- Privacy: **fails AC5**. A transcript holds everything the session saw, including what rule 9 keeps
  unread.
- Countable: only after parsing each harness's format.

### Option D: a hook writes the trace

- Fit: **fails**. A hook never holds a rule and is never the only road to a behaviour (`CLAUDE.md`,
  "`hooks/` never holds a rule"). A hook also cannot see which step of a skill ran. Cursor has no
  matching event, and Codex has not been seen to fire one for a skill.

### Option E: a shared run-trace rule every skill follows, read by `tailor --feedback --runs` (chosen)

- Unwatched runs: yes. The run writes its own trace wherever it runs.
- Countable: yes. The shape is fixed in `shared/run-trace.md`.
- Gates and privacy: written under rule 9, never staged, sent nowhere.
- Fit: one shared file, one rule, one flag on `tailor`.
- Cost: a few lines per run, on by default, measured before release (see Performance).

### Scores

| Criterion | A: today | B: journal skill | C: transcripts | D: hook | E: shared rule |
|-----------|----------|------------------|----------------|---------|----------------|
| 1. Unwatched runs | no | no | partly | partly | yes |
| 2. Countable | no | no | after parsing | partly | yes |
| 3. Gates and privacy | yes | yes | no | yes | yes |
| 4. Fit | yes | duplicates `tailor` | harness-specific | breaks the hook rule | yes |
| 5. Cost per run | none | none unless invoked | none | small | small |

## Chosen approach: Option E

### Where a trace lives

- **Path:** `<docs root>/derived/traces/<skill>/<run-id>.md`. `<run-id>` is `<YYMMDD-HHMM>-<slug>`, as
  for a progress log (`artifact-paths.md:323-324`).
- **One directory for every skill.** That gives one exclude line, `/<docs root>/derived/traces/`,
  added and checked the way a progress log's line is (`artifact-paths.md:325-333`). The check is
  mandatory, because the trace is on for everyone. Where `git check-ignore -q` fails, the run writes no
  trace and says why before its first step.
- **Group: Derived.** Safe to delete, never staged, never committed.
- **A trace is not a progress log.** A skill with a progress log still writes it; the trace sits apart
  and serves analysis, not resuming.

### What a trace holds

`shared/run-trace.md` fixes the shape. One fact per line, each with its time:

```
skill: implement | kit: 0.1.8 | harness: codex 0.162.1 | way: pane | flags: --no-review
subject: #15 | branch: feat/15-export | start: 6dfab99 | profile: present | override: none
15:32 step 2 plan gate: straight through, plan path given
15:33 gate approval: asked Lam Ngoc Khuong, waited 1m 40s, answered
15:41 step 5 verify by layer: lint ran, test skipped (no Test command in the profile)
15:44 commit: staged only, committed by the coordinator (sandbox)
15:50 review: 1 BLOCKING, 2 SHOULD FIX, round 2 of 2
end: docs/records/implementations/261011-1532-15-export.md
```

- **The header** carries:
  - the skill;
  - the kit version from the plugin manifest beside the skill, or `unknown`;
  - the harness and its version where the harness says;
  - the way the run was started: `session`, `subagent`, or `pane`;
  - the flags and the subject, with the subject written as a progress log writes it;
  - the branch and start commit;
  - whether a profile and an override were found, and whether the override applied.
- **Event kinds**, and no others:
  - `step <n> <name>`: ran, skipped with the reason, or failed;
  - `gate <kind>`: who was asked, how long it waited, whether it was answered;
  - `stop`: a ceiling or an escalation, with the person named;
  - `review`: counts by severity, and the round of the ceiling;
  - `corrected by hand`: what a person changed afterwards, in that person's words, written only when
    that person says it;
  - `end`: the artifact path, `no artifact:` and why, or `interrupted`.
- **What a trace never holds:**
  - conversation text, a file's content, a command's output, or a secret value;
  - a person's data or an internal host, masked as `<redacted: kind>` by the same list a progress log
    uses (`artifact-paths.md:343-347`);
  - a judgement of the run, such as "went well". Only facts another reader could check.
- **Names stay.** The names of team members who answered a gate stay, because who waited for whom is
  the point. A trace stays in the project; `tailor` neutralizes anything it sends to the kit, per
  `CONV-010`.

### Who writes it, and when it is off

- **Rule 10 of `team-roles.md`:** "Leave a run trace, per `shared/run-trace.md`, unless the profile
  says `Run trace: off`." Every skill already reads that file, so no `SKILL.md` needs a new citation.
- **The switch.** A missing line, and a missing profile, mean on (AC3). There is no per-run switch
  (AC4). A person who wants one run untraced deletes that trace, which costs nothing because it is
  derived.
- **`atk:init`** asks the line when it writes a profile, saying what a trace holds. `--audit` reports
  it as missing without treating that as a defect, since missing means on.
- **The profile line changes behaviour, not a path,** like `Contract`. `project-profile.md` names it
  beside `Contract` (`:200-203`).

### Retention

- **Keep the twenty newest traces of each skill.** When a run creates a trace, it removes the oldest
  beyond twenty in that skill's directory.
- **Removal is bounded.** It removes only files whose names match the `<run-id>.md` pattern, and only
  in that directory.
- **`tailor --feedback --runs` never deletes what it read.**

### Reading many traces: `atk:tailor --feedback <skill> --runs`

- **Input.** `--runs` takes a directory, or nothing for `<docs root>/derived/traces/<skill>/`. It reads
  every trace there, or those since `--since <YYYY-MM-DD>`.
- **Patterns, counted.** It looks for:
  - a step skipped in most runs;
  - a gate that waited longest;
  - a ceiling reached repeatedly;
  - `BLOCKING` findings of one kind;
  - the same `corrected by hand` line in several runs.

  Each pattern carries its count, "step 5 skipped in 9 of 12 runs", and the run-ids behind it.
- **Each pattern goes through the fork** of `feedback.md`, one at a time, exactly as a finding does
  today: an override for this team, a record for the author, or neither.
- **The record.** "The run" table becomes "The runs": count, date range, harnesses, and ways. Findings
  cite the run-ids.
- **Without `--runs`, `--feedback` behaves as today.**

### `atk:orchestrate`

- **A job's trace is written in its worktree.** Before the coordinator removes a worktree, it copies
  the job's trace into its own `<docs root>/derived/traces/<skill>/`. A trace in a removed worktree is
  lost, and the coordinator's tree cannot see the worktree's directory (`artifact-paths.md:375-376`).
- **The coordinator writes its own trace too:** each job's way, the agent kind, its waits, and its
  outcome.
- **The job result file of the orchestrate design stays**, whether traces are on or off, because the
  coordinator needs it to continue the chain. The trace is for analysis afterwards.

## Decisions recorded

- Traces are on by default and turned off in `.atk/profile.md`. Lam Ngoc Khuong, 2026-10-11.
- There is no per-run switch. Lam Ngoc Khuong, 2026-10-11.
- No journal skill. The judgement stays in `atk:tailor --feedback`. Lam Ngoc Khuong, 2026-10-11.
- The obligation is rule 10 of `team-roles.md`, not a section of `artifact-paths.md`. A trace is an
  obligation of every run, including runs that write no artifact, such as `atk:help` in state mode,
  which may never open `artifact-paths.md`. "Nine rules" changing in five files is the accepted cost.
  Lam Ngoc Khuong, 2026-10-11.
- Twenty traces per skill, fixed, not set in the profile, so the profile gains one line only. Lam
  Ngoc Khuong, 2026-10-11.
